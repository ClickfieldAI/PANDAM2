## 1. Architecture as found

- **Auth**: password (PBKDF2) + optional Google/Apple ID-token login; sessions are SHA-256-hashed tokens in D1; Bearer token on native (SecureStore), HttpOnly cookie on web. `authMiddleware` + `requireAuth` on routes; identity always from the session. Tested (`auth`, `account`, `oauth` tests).
- **Domain rules** (pure): `domain/offers.ts`, `domain/barter.ts`, `domain/payment.ts`, `domain/reviews.ts`, `domain/matching.ts`, `domain/recommendations.ts`, `domain/platform-fee.ts`.
- **Data access**: thin repositories in `packages/database`. D1 offers **no interactive transactions**; only `batch()`. Repositories take the driver-agnostic `BaseSQLiteDatabase` type, so there is currently **no transactional primitive** anywhere in the codebase.
- **Realtime**: none. Chat, typing and notifications are **HTTP polling** (4 s messages, 15 s conversations, 20 s notifications, ~typing poll). The `CONVERSATION` Durable-Object binding in `env.ts` is declared but not wired.
- **Push**: Expo push via `lib/push.ts` + token registry; the notification row is stored first, push is best-effort (tested with a fake sender in `push.test.ts`).
- **Payments**: Razorpay Payment-Link scaffolding (`routes/payments.ts`, `lib/razorpay.ts`) with HMAC-verified webhook — **no live credentials**, so never executed against Razorpay.
- **Demo-data seam**: `apps/app/src/dummy` is off unless `EXPO_PUBLIC_DEMO_DATA=1` (default off). Not a production concern, but it is wired into 5 screens and must stay off for release builds.

## 3. Defects and security risks (ranked)

1. **HIGH — Unilateral trade completion.** One party can mark an exchange completed (and thereby unlock reviews) with no confirmation from the other. [probed]
2. **HIGH — Non-atomic accept + no CAS.** Partial failure leaves inconsistent state; concurrency safety on D1 is unproven. [read + partial probe]
3. **HIGH — Expired and stale offers acceptable.** Expiry never enforced; acceptance ignores whether the offered item is still available. [probed]
4. **HIGH — Cancelled transactions permanently remove listings from the market.** [probed]
5. **MEDIUM — Verification is self-service in non-production** and impossible in production (deployment blocker).
6. **MEDIUM — No rate limiting** on auth, offers, messaging, uploads.
7. **MEDIUM — Image uploads trust the declared MIME type.**
8. **MEDIUM — Duplicate message on retry; no delivery state.** [probed]
9. **MEDIUM — Cosmetic favourites** present users with a feature that does nothing.
10. **LOW — Reports are write-only; no blocking; N+1 queries in transaction/offer hydration; no crash reporting in the worker.**

## 4. Dependencies and blockers

- **Real identity verification provider (DigiLocker/face)** — external service + credentials. _BLOCKED_ for production.
- **Razorpay credentials** — payments never exercised live. _BLOCKED_.
- **Physical iOS/Android devices** — push delivery, haptics, camera/gallery picker, Lottie performance, keyboard behaviour. _Unverifiable here_.
- **Cloudflare deployment / Durable Objects** — real-time chat transport and production D1 behaviour need an approved deployment (explicitly out of scope without approval).
- **Product decisions**: relist policy on cancel (this plan assumes "restore to `published` if the owner hasn't changed it"), counter-offer semantics (assumed: a counter supersedes the original and creates a new pending offer in the reverse direction), listing-delete policy (assumed: soft-delete/archive when referenced), admin roles (assumed: `is_admin` flag on users).

## 5. Required tests (summary)

State-machine and authorization tests for every new transition; SQL-level atomicity tests (conditional-update loser gets a clean error, unique-index duplicates); idempotent-retry tests; migration-on-populated-data tests; app unit tests for hooks/selectors that decide button availability; and a documented manual device checklist for what automation cannot reach.

## 6. Priorities and realistic estimates

See `DEVELOPMENT_ROADMAP.md`. Rough total to a defensible production candidate: **~5–7 engineer-weeks**, excluding the external blockers above.

Manual run (web build, local worker + D1; simulated by patching `fetch` in the page): (1) _response lost_ — the request reached the server but the client never saw the reply: one stored message, the queue drained itself when the next poll returned it, the bubble ended as "Sent"; (2) _offline_ — three retries with growing delays, the message persisted in `localStorage`, nothing on the server; (3) _restart while offline→online_ — after a page reload the restored queue sent automatically, once, under its original id; (4) _"Seen"_ appeared only after the partner's client called read; (5) _blocked_ — "Not sent · This person is not available." with Retry/Delete and no endless retries.

Limitations: photo messages are sent directly (not queued) because they need an upload first; read receipts are always on (no setting to turn them off — a product decision); the React provider/hook itself has no automated test (the rules it applies do); native (iOS/Android) behaviour of `AppState` and `AsyncStorage` retry is unverified; unread/"seen" updates arrive on the polling interval, not instantly.

**Defects found and fixed in this milestone**

1. **HIGH — CSRF on cookie-authenticated writes.** The web session cookie is `SameSite=None` and bodies were parsed regardless of `Content-Type`, so a hostile site could send a "simple" `text/plain` POST carrying a victim's cookie and have it executed. Fixed with an Origin check for cookie-authenticated writes (bearer-token and origin-less clients exempt).
2. **MEDIUM — localhost was in the production CORS allowlist.** `DEV_ORIGINS` were merged into the allowed set in every environment, so a page on `localhost` could make credentialed calls to a production API. Dev origins now apply only when `PANDAM_ENV=development`.
3. **LOW — no request-size bound on JSON bodies** (now 100 KB; uploads keep their own 8 MB cap).

**Limitations / decisions**

- Fixed-window limiting allows up to about double the limit across a window boundary.
- IP-based limits depend on traffic arriving through Cloudflare; behind another proxy `CF-Connecting-IP` is absent and IP limits are skipped (per-user limits still apply).
- Failing open on limiter errors is a deliberate availability choice; a stricter policy for sign-in could be chosen.
- The Origin check does not protect a request with no `Origin` header (non-browser clients), which is intended.
- Sentry setup (DSN secret, release label) and the thresholds above are documented in `docs/architecture/security-and-operations.md`; **no secret was added to the repo**.
